# Срез 3 — серверное хранилище agent-sync

Статус: **план подтверждён; slice 3 реализован и локально проверен**. Инструкция и результаты: [server.md](server.md). Проверка реальной Tailscale-изоляции остаётся условием развёртывания.

## 1. Что уже согласовано

- Сервер находится на Xeon и работает в Docker под Linux.
- Клиенты подключаются через Tailscale.
- Отдельного API-токена нет. Сетевой доступ разрешается правилами Tailscale только доверенным устройствам; доступный по сети API не проводит дополнительную авторизацию клиента.
- Сервер только хранит данные: он не должен получать ключ расшифрования или читать сообщения.
- Поиск через локальную SQLite `catalog.db` и MCP из срезов 1–2 остаются на клиенте.

Решения ниже подтверждены пользователем. Развёртывание на Xeon, миграция действующего GitHub-хранилища и релиз остаются отдельными операциями.

## 2. Результат первого серверного среза

Можно создать новое хранилище на своём сервере, подключить два Windows-клиента и синхронизировать историю без Git/GitHub в этом пути выполнения.

Серверная БД — PostgreSQL. Между клиентом и БД находится небольшой API: клиент не получает пароль PostgreSQL и не подключается к её порту напрямую.

```text
Windows-клиент A                         Windows-клиент B
нативные сессии                         нативные сессии
локальный поиск / MCP                   локальный поиск / MCP
шифрование и проверка данных            шифрование и проверка данных
          │                                      │
          └──────────── Tailscale ────────────────┘
                              │
                     agent-sync server API
                              │
                       PostgreSQL volume
                 зашифрованные объекты и индекс
```

GitHub остаётся источником кода и релизов программы. Существующий Git-backend сохраняется для совместимости; использование серверного backend не должно создавать Git-клон или проверять приватность GitHub-репозитория.

**Важная граница:** этот срез добавляет рабочий backend для нового хранилища. Автоматический перенос существующего GitHub-хранилища и переключение уже подключённых устройств предлагается вынести в отдельный шаг; см. раздел 10. До него текущая установка пользователя не переключается автоматически.

## 3. Что входит и что не входит

Входит:

- HTTP API и PostgreSQL со схемой версии 1.
- Dockerfile и Compose для Xeon; постоянный volume БД.
- Новый HTTP storage provider и gateway для начального подключения.
- Ограничение доступа через Tailscale и безопасные сетевые настройки развёртывания, без отдельной авторизации API.
- `init`, `join`, `push`, `pull`, `sync`, `status`, `doctor` и разрешение конфликтов через новый backend.
- Работа фонового агента с выбранным backend.
- Документация установки, доступа, резервного копирования и восстановления.
- Проверки на настоящей PostgreSQL и двух синтетических клиентах.

Не входит:

- Серверный поиск, MCP, эмбеддинги, векторная БД, извлечение памяти и запуск моделей.
- Веб-интерфейс, регистрация пользователей, права на отдельные чаты и полноценная мультитенантность.
- Публичный интернет-доступ и автоматическая настройка Tailscale.
- Портирование клиентского CLI и DPAPI на Linux: Linux поддерживается сервером, клиент пока Windows.
- Автоматический перенос/удаление GitHub-данных, удаление репозиториев API-командой, ротация ключа шифрования.
- Автоматическая очистка старых объектов, история версий для пользователя, обещание бессрочного восстановления удалений.
- Развёртывание на настоящем Xeon, изменение установленного CLI, коммит или релиз без отдельной команды пользователя.

## 4. Компоненты и совместимость

| Компонент | Ответственность |
|---|---|
| `CodexHistorySync.Core` | Существующая логика сканирования, шифрования, конфликтов, безопасного импорта и локального состояния |
| `CodexHistorySync.Remote` | Контракты протокола, проверка адреса, HTTP-клиент, реализация `IStorageProvider` |
| `CodexHistorySync.Server` | ASP.NET Core API, ограничения запросов, транзакционное хранилище PostgreSQL |
| CLI gateway / composition | Выбор Git или HTTP по проверенному адресу, `init`/`join`, диагностика |
| Docker Compose | API и PostgreSQL, volume, секрет БД, health checks и сетевые привязки |

Согласованный стек: .NET 10, PostgreSQL 17, Npgsql 10.x. В реализации фиксируются конкретные проверенные версии зависимостей; образы не используют тег `latest`.

Сервер не ссылается на Windows-проект и не содержит нативных парсеров сессий. При необходимости общие контракты отделяются так, чтобы серверу не требовались SQLite и клиентские компоненты.

Сохраняются:

- Формат `CHS1`, AES-256-GCM и существующие правила аутентификации индекса/объектов.
- Формат manifest и Argon2id-параметры; никаких серверных ключей расшифрования.
- Существующие виды объектов, включая названия/описания сессий и Claude memory.
- Правила нормализации перед синхронизацией. Это не новый механизм побайтового резервирования всех файлов агента.
- Локальные резервные копии, tombstone-записи, конфликты и отказ от небезопасного импорта.
- Совместимость старых конфигураций с GitHub; без неявного изменения схемы их данных.

HTTP provider должен освобождать сетевые ресурсы при завершении операции, включая обёртку предварительного просмотра `join`. Поиск, MCP, `--sessions` и `update` не должны начинать подключаться к серверу из-за изменения composition.

## 5. Безопасность и доступ

### Шифрование и видимость метаданных

Клиент шифрует данные до отправки. Ключ кэшируется через Windows DPAPI; пароль вводится скрыто, как сейчас. Сервер получает только ciphertext и публичный аутентифицированный manifest.

Сервер видит имя хранилища, непрозрачные идентификаторы, хеши ciphertext, размеры, число объектов, ревизии и время запросов. Он не получает тексты сообщений, названия сессий или пути исходных файлов в открытом виде. Имя хранилища следует выбирать без чувствительной информации.

Уточнение реализации: старый CHS1-заголовок аутентифицирован, но открыт и содержит native logical ID (у памяти Claude — закодированный проект и имя файла). Для соблюдения этой границы HTTP-провайдер шифрует весь исходный объектный конверт внешним CHS1 с opaque ID, фиксированным generic kind и отдельным HKDF-derived ключом. Сервер ключ не получает; Core/Git не меняются. Тесты проверяют реальные бинарные заголовки в PostgreSQL, не только отсутствие canary в SQL-тексте.

Проверка SHA-256 на сервере защищает целостность передачи, но не заменяет проверку AES-GCM и индекса на клиенте. Наличие заголовка `CHS1` тоже не доказывает, что данные корректно зашифрованы: сервер без ключа этого проверить не может.

Компрометация сервера или устройства, которому разрешено подключение к API, может нарушить доступность данных, подменить ответы или вернуть старый снимок. Аутентификация ciphertext обнаруживает подделку содержимого, но этот срез не добавляет независимую защиту от злонамеренного отката к ранее корректному снимку. Резервные копии и сохранность клиентского пароля остаются обязательными.

### Доступ без API-токена

- Авторизацию сетевого подключения выполняет Tailscale: разрешаются только выбранные доверенные устройства, а не любой участник tailnet.
- В API нет Bearer-токена, логина, отдельного клиентского секрета и команд `server login`/`server logout`.
- Один экземпляр сервера предназначен для одного владельца. Любой процесс, получивший сетевой доступ к API, может читать ciphertext и выполнять операции записи во всех его хранилищах. Разделения прав по пользователям/репозиториям нет.
- Ключ и пароль шифрования нужны клиенту для чтения и аутентификации истории, но **не являются авторизацией запросов API**. Незнание ключа не мешает атакующему нарушить доступность хранилища, если сетевой доступ ему уже открыт.
- Отзыв доступа устройства производится через правила доступа или управление устройствами Tailscale, без смены пароля шифрования.
- Windows DPAPI продолжает защищать ключ шифрования; дополнительного DPAPI-хранилища API-учётных данных нет.
- Пароль PostgreSQL сохраняется как отдельный серверный секрет. Клиент его не знает: отказ от API-токена не означает отказ от аутентификации БД.
- Процессы самого Xeon и контейнеры с доступом к внутренней сети считаются доверенными. Проверка одного только диапазона IP в приложении не заменяет сетевую изоляцию.

### Сеть

- По умолчанию опубликованный порт API привязан к `127.0.0.1` на Xeon.
- Для прямого доступа через Tailscale оператор явно задаёт Tailscale IP хоста в привязке порта. Публикация API на `0.0.0.0`, LAN-адресе или публичном интерфейсе не поддерживается: без дополнительной авторизации это откроет все операции API доступным узлам.
- PostgreSQL не публикует порт на хост; API обращается к ней по внутренней Docker-сети.
- Внутри контейнера API слушает контейнерный интерфейс; ограничение внешнего доступа задаётся привязкой порта на хосте и правилами tailnet.
- На хосте также проверяется фильтрация входа к опубликованному порту: внешний доступ только через Tailscale, а не через LAN-интерфейс с маршрутом до Tailscale IP. Правила должны учитывать обработку трафика Docker; одной строки привязки IP недостаточно для доказательства изоляции.
- HTTP допускается для буквального Tailscale IP или loopback. Для DNS-имени `*.ts.net` используется HTTPS с обычной проверкой сертификата, например через отдельно настроенный Tailscale Serve.
- Клиент отказывается от произвольных публичных HTTP-адресов, credentials в URL, query/fragment и неоднозначных путей.
- Перенаправления HTTP не выполняются: запросы данных не должны уходить на другой адрес. Для прямого обращения в tailnet не используются системные HTTP-прокси.
- Сам адрес из `100.64.0.0/10` не доказывает наличие Tailscale: оператор должен проверить маршрутизацию и ACL/grants. Наличие Tailscale само по себе не доказывает, что нежелательные устройства запрещены правилами. Tailscale на Xeon устанавливается и настраивается отдельно.
- При использовании Tailscale Serve проксируется только loopback-порт; публичная публикация через Funnel не входит в поддерживаемую конфигурацию.
- До использования реальных данных проверяется недоступность API из LAN, интернета и с неразрешённого tailnet-устройства. Эти проверки — условие развёртывания, не опциональная рекомендация.
- API не предназначен для браузера: не включать CORS, отклонять запросы с `Origin`, проверять допустимые Host и типы содержимого изменяющих запросов. Проверить, что сторонняя веб-страница на разрешённом ПК не может вызвать операции записи через браузер.

Логи не содержат пароли, ключи, тела запросов, ciphertext целиком или SQL-параметры с данными. Наружу возвращаются короткие стабильные ошибки, без stack trace и текста исключений БД.

## 6. Схема PostgreSQL

Не создаём таблицу сообщений: сервер не знает семантику сессий.

| Таблица | Основные поля и назначение |
|---|---|
| `schema_version` | Версия схемы БД |
| `repositories` | `name` PK, `manifest bytea`, `encrypted_index bytea`, `revision`, временные метки |
| `blobs` | `(repository_name, ciphertext_sha256)` PK, `ciphertext bytea`, размер, время создания |
| `object_refs` | `(repository_name, opaque_object_id)` PK, ссылка на соответствующий blob |

Для ссылок используются внешние ключи в пределах одного хранилища. Нельзя опубликовать ссылку на blob другого хранилища или на отсутствующий blob.

`blobs` неизменяемы: повторная загрузка тех же байтов по тому же хешу идемпотентна. Хеш вычисляется по ciphertext, не по открытому тексту. Это устраняет повторную отправку одного и того же зашифрованного объекта при ретраях, но не обещает дедупликацию независимо перешифрованных сообщений.

`object_refs` и `encrypted_index` описывают только текущий опубликованный снимок. `revision` — непрозрачный уникальный идентификатор, а не время или Git SHA. Старые blob-данные сохраняются для чтения уже полученных снимков, но отдельного каталога исторических снимков в этом срезе нет.

Инициализация создаёт manifest, пустой зашифрованный индекс и первую ревизию одной транзакцией. Повторный `init` существующего имени не перезаписывает данные. Одновременные `init` одного имени: ровно один успешен.

Схема применяется транзакционно, с блокировкой от одновременного запуска миграции двумя API-процессами. Неизвестная более новая схема останавливает запуск, а не вызывает попытку её исправить. Все значения передаются SQL-параметрами.

## 7. Протокол API v1

Все маршруты находятся за сетевой границей Tailscale/локального хоста и работают без прикладного токена. Минимальный liveness endpoint не содержит сведений о хранилищах; readiness с проверкой БД не раскрывает диагностические секреты.

| Метод и маршрут | Назначение |
|---|---|
| `GET /healthz` | Минимальный ответ о работе процесса |
| `GET /v1/info` | Проверка доступности API и поддерживаемой версии протокола; не проверка прав клиента |
| `PUT /v1/repositories/{name}` | Создать отсутствующее хранилище с manifest и пустым encrypted index |
| `GET /v1/repositories/{name}/setup` | Manifest, индекс и ревизия для подключения |
| `GET /v1/repositories/{name}/snapshot` | Согласованный индекс, ревизия и пары `opaque_object_id → ciphertext_sha256` |
| `PUT /v1/repositories/{name}/blobs/{hash}` | Загрузить ciphertext, проверить размер и хеш |
| `GET /v1/repositories/{name}/blobs/{hash}` | Прочитать конкретные неизменяемые байты |
| `POST /v1/repositories/{name}/publish` | Атомарно применить изменения при совпадении ожидаемой ревизии |

Blob передаётся как бинарное тело, не как base64 внутри большого JSON. Маленькие контракты и encrypted index — JSON; для byte-полей учитывается увеличение размера при base64.

Согласованные начальные ограничения:

- Имя хранилища: 1–64 символа, lowercase ASCII, цифры и дефис.
- Идентификатор объекта и хеш ciphertext: 64 hex-символа.
- Manifest: до 64 KiB; encrypted index: до 16 MiB.
- Один ciphertext blob: до 100 MiB. Существующий клиентский предел нормализации пока не увеличивается.
- Не более 100 000 ссылок на объекты в снимке/публикации.
- JSON-запрос/ответ: до 64 MiB, включая base64 и список ссылок.
- Ограниченные таймауты и количество одновременных тяжёлых запросов; никакого накопления всей истории в памяти API.

Значения проверяются как на клиенте, так и на сервере; превышение лимита явно отклоняется, данные не обрезаются. Чтение тела ограничивается и при отсутствии `Content-Length`.

Ошибки различаются: недоступность сетевого подключения, неизвестное хранилище, конфликт ревизии, невалидный объект, слишком большой запрос, временная недоступность БД. Клиент не трактует сетевой отказ, `404`/`500` как пустой снимок и не начинает из-за этого удалять локальные сессии. Недоступность из-за правил Tailscale не обязана возвращать HTTP-ошибку: возможны таймаут или отказ соединения.

## 8. Одновременные записи и сбои

Последовательность публикации:

1. Клиент получает согласованный снимок ревизии `R` и проверяет encrypted index своим ключом.
2. Существующий sync engine рассчитывает изменения.
3. Клиент загружает новые ciphertext blobs. Они ещё не меняют опубликованный снимок.
4. Клиент отправляет ожидаемую ревизию `R`, новый индекс и изменения ссылок.
5. Сервер открывает транзакцию и блокирует строку соответствующего хранилища.
6. При несовпадении ревизии возвращает конфликт с текущей ревизией, ничего не публикуя.
7. При совпадении проверяет все ссылки, обновляет индекс/ссылки/ревизию и коммитит их вместе.
8. Клиент выполняет дальнейшие действия и сохранение локального baseline по существующим правилам sync engine.

Чтение метаданных выполняется в одном согласованном снимке PostgreSQL. Последующие загрузки объектов используют закреплённые хеши: переключение текущей ревизии другим ПК не меняет байты, которые читает первый.

| Ситуация | Ожидаемое поведение |
|---|---|
| Два ПК публикуют от одной ревизии | Один выигрывает; второй перечитывает снимок и перепланирует, используя существующий предел пяти попыток |
| Обрыв загрузки blob | Текущий снимок не меняется; неполное тело не становится допустимым blob |
| Ошибка БД посреди публикации | Полный rollback индекса, ссылок и ревизии |
| Ответ потерян после успешного коммита | Клиент не считает операцию подтверждённой; следующая синхронизация перечитывает реальное состояние и сходится без потери данных |
| Не хватает места | Публикация не оставляет частично обновлённый снимок; ошибка не замалчивается |
| Подмена ciphertext или индекса | Клиент останавливается до небезопасной локальной мутации/baseline advancement |
| Устаревший клиент не знает протокол | Явный отказ при проверке версии |

Удаление сессии по-прежнему определяется аутентифицированными tombstone-записями клиента. Отсутствие blob, сетевой сбой или пустой ответ сервера не заменяют tombstone.

## 9. CLI и подключение

Публичный интерфейс для новой, ещё не подключённой установки:

```powershell
# На первом ПК: создать новое хранилище; пароль шифрования вводится скрыто.
agent-sync init http://100.101.102.103:8080/v1/repositories/personal
agent-sync push

# На втором ПК: ввести пароль шифрования и посмотреть план подключения.
agent-sync join http://100.101.102.103:8080/v1/repositories/personal
agent-sync join http://100.101.102.103:8080/v1/repositories/personal --apply

# Дальнейшая работа не зависит от backend.
agent-sync sync
agent-sync status
agent-sync doctor
```

Адрес — пример, его нужно заменить реальным Tailscale IP Xeon.

Отдельного входа в API нет. Перед `init`/`join` клиент проверяет допустимость адреса, доступность `/v1/info` и версию протокола. Проверка прав на сетевое подключение остаётся за правилами Tailscale; успешный ответ API не доказывает правильную настройку этих правил.

`init`/`join` по-прежнему запрашивают пароль шифрования скрыто. Ошибочный пароль не допускает импорт истории; это проверка подлинности данных на клиенте, а не серверный логин.

`init`/`join` серверного backend отказываются незаметно заменить уже выбранное другое хранилище. `doctor` проверяет доступность API и схему вместо обязательных проверок Git/приватности GitHub. При недоступном Tailscale/API фоновый агент сообщает о сетевой ошибке и повторяет попытку по существующим правилам, без интерактивного ввода.

Новый backend не требует второй копии локальной истории: нативные файлы и существующий каталог остаются на месте. Состояние синхронизации и ключи изолированы по repository ID.

## 10. Переход с существующего GitHub-хранилища

**Не выполнять `init` нового сервера поверх текущей настройки как способ миграции.** Можно потерять связь с baseline, пропустить удалённые объекты или неправильно обработать удаления/конфликты.

Согласованная граница первой реализации:

- Серверный backend проверяется на отдельных тестовых конфигурациях и новых подключениях.
- Текущий GitHub-репозиторий, настройки пользователя и фоновые агенты не изменяются.
- Автоматической команды миграции в первом серверном срезе нет. Практическое переключение нынешней установки будет отдельным обязательным этапом перед повседневным использованием нового backend.

Следующий этап миграции должен предусмотреть:

1. Остановку фоновой синхронизации на всех устройствах и резервирование локального состояния.
2. Проверку актуального Git-снимка и разбор незавершённых конфликтов.
3. Перенос **согласованного зашифрованного снимка**, включая manifest, encrypted index, annotations, memory и tombstones, а не повторную отправку только файлов одного ПК.
4. Сохранение repository ID и форматов шифрования там, где это необходимо для их аутентификации.
5. Загрузку в неопубликованное пустое назначение и атомарное открытие полного снимка только после проверки всех объектов. Для этого нужен отдельный протокол импорта; обычный `init` недостаточен.
6. Явное переключение клиента с безопасным обновлением backend-specific revision/baseline, затем подключение остальных устройств.
7. Проверку сходимости двух ПК и восстановления из резервной копии.
8. Возможность отката. Удаление GitHub-репозитория — только отдельным решением после успешной проверки.

Если важно перенести текущую установку сразу в рамках среза 3, этот этап нужно включить в согласованный объём **до** начала реализации. Это расширение, а не скрытая часть `init`.

## 11. Старые объекты, объём и резервное копирование

В первой версии **нет автоматического GC**: старые или неиспользуемые ciphertext blobs сохраняются. Это относится и к успешно загруженным объектам неудавшейся публикации.

Причина: клиент может ещё читать предыдущий снимок. Удалить blob сразу после смены ссылки — значит сломать такое чтение. Корректная очистка требует отдельной политики retention/leases или другого согласованного протокола.

Следствия:

- Размер БД растёт быстрее размера текущей истории.
- Удаление сессии из текущего снимка не означает физического стирания её ciphertext.
- Это не пользовательская история версий: наличие старого blob не гарантирует удобного или полного восстановления старого состояния.
- В документации нужны контроль размера БД/volume, предупреждение о заполнении диска и отсутствие обещания автоматического освобождения места.
- Не добавлять «очистку» путём ручного удаления строк из `blobs`: можно нарушить активные чтения или восстановление.

Резервирование:

- Согласованный `pg_dump` всей выделенной БД; хранение копии отдельно от рабочего volume.
- Отдельное сохранение конфигурации развёртывания, правил сетевого доступа и секрета БД в защищённом месте.
- Пароль шифрования — в менеджере паролей владельца, не в серверной БД. Бэкап ciphertext без этого пароля не восстанавливает историю.
- Проверка `pg_restore` в **новую тестовую БД**, затем подключения синтетического клиента и проверки содержимого.
- Запрет на инструкции вида `docker compose down -v` в обычном обновлении сервера: удаление volume не является обновлением.

## 12. Развёртывание и обновление

- Dockerfile API: multi-stage build, Linux runtime, запуск непривилегированным пользователем.
- Compose: API, PostgreSQL, отдельная внутренняя сеть, постоянный volume, секрет БД и health checks; API-токен не генерируется и не монтируется.
- Read-only filesystem API, если необходимые временные каталоги вынесены отдельно; секрет БД монтируется только для чтения с проверкой прав доступа.
- API не получает Docker socket, SSH-ключи, каталог пользователя или каталоги истории агентов.
- PostgreSQL стартует и проходит health check до готовности API; запуск проверяет версию схемы.
- Конкретные команды резервирования, обновления образа без удаления volume и проверки состояния описаны в `docs/server.md`.
- Конфигурация ограничений памяти/параллелизма проверяется нагрузочным тестом с большими объектами; характеристики Xeon не предполагаются заранее.
- Нет автоматического SSH/deploy на Xeon. После локальной проверки оператор отдельно разрешает или выполняет развёртывание.

Версия API и версия клиентского релиза — отдельные понятия. Несовместимое изменение API не прячется за patch-обновлением сервера.

## 13. Порядок реализации после согласования

1. **Контракты и ограничения:** адреса, модель снимка, CAS, ошибки, тесты валидации. Проверить зависимости серверного проекта, чтобы не потянуть Windows/SQLite без необходимости.
2. **PostgreSQL:** схема v1, инициализация, согласованное чтение, immutable blobs, транзакционная публикация. Тесты на реальной БД.
3. **API:** маршруты без токена, защита от браузерных запросов, ограничения тел/параллелизма, безопасные ошибки, health/readiness; сетевую изоляцию задать в развёртывании.
4. **HTTP-клиент и provider:** bounded reads, проверка хешей, закреплённые ссылки, освобождение ресурсов, запрет перенаправлений и проверка версии через `/v1/info`.
5. **CLI:** gateway без дополнительных учётных данных API, выбор backend, init/join guards, диагностика и фоновый агент.
6. **End-to-end:** два устройства, конфликты, сбои, plaintext canaries, совместимость существующего Git-пути.
7. **Поставка:** Linux API, Compose, Windows single-file CLI, инструкция, backup/restore drill.
8. **Ревью результата:** отдельно решение о миграции нынешней установки, развёртывании и релизе.

## 14. Критерии приёмки

Срез считается завершённым только после проверки следующих сценариев:

- Два синтетических Windows-клиента сходятся через HTTP/PostgreSQL; в этом пути не запускаются `git` и `gh`.
- Синхронизируются все поддерживаемые виды данных, а локальные поиск/MCP продолжают работать.
- Нет plaintext canary сообщений/названий/путей в таблицах БД, API-логах и резервной копии. Публичный manifest и перечисленные метаданные проверяются отдельно, а не ошибочно объявляются секретным ciphertext.
- Разрешённый клиент выполняет API-операции без `Authorization` и дополнительного логина; отдельный API-секрет не создаётся и не сохраняется.
- Перед развёртыванием с реальными данными проверяется: API недоступен из LAN/интернета/неразрешённого tailnet-устройства, разрешённые устройства подключаются. PostgreSQL не публикуется на хосте. Локальные тесты с loopback не заменяют проверку реальных правил Tailscale.
- URL, редиректы, браузерные запросы, malformed JSON и слишком большие chunked-тела не обходят ограничения. Пароль PostgreSQL и клиентское шифрование продолжают работать независимо от отсутствия API-токена.
- Одновременные init и публикации имеют однозначный результат; конфликт не оставляет частичного снимка.
- Старый снимок читается после новой публикации; отсутствующий или повреждённый blob не трактуется как удаление.
- Отключение БД, отмена операции и потеря ответа не приводят к частичному локальному импорту или неверному продвижению baseline.
- Сохраняются конфликтующие версии, tombstones и существующие гарантии безопасного импорта.
- Перезапуск API/PostgreSQL с тем же volume сохраняет данные; backup/restore проверен в изоляции.
- Собираются Linux-сервер и Windows single-file CLI; проверяются Compose и regression tests Git-backend.
- Лимиты проверены с крупным blob и большим числом ссылок, а не только на коротких строках.

Один mock-тест вместо PostgreSQL или только успешная сборка не считаются проверкой транзакционной корректности. Для реализации запущены изолированные локальные PostgreSQL/Compose-проекты с синтетическими данными; реальная Tailscale-изоляция проверяется отдельно перед развёртыванием.

## 15. Подтверждённые границы среза

Подтверждены следующие значения:

| Решение | Предложение | Последствие |
|---|---|---|
| Миграция текущего GitHub-хранилища | Отдельный следующий шаг | Срез 3 даёт backend, но ещё не переключает твою нынешнюю установку |
| Очистка старых blobs | Без GC в первой версии | Стабильные чтения; требуется контроль роста БД |
| Подключение | Прямой Tailscale IP; HTTPS для tailnet DNS | Не требуется публичный домен, но нужно настроить привязку порта и ACL |
| ОС клиента | Пока Windows | Linux на Xeon относится к серверу, не к CLI |

Перенос действующего GitHub-хранилища не входит в этот срез; существующая установка не переключается.

## 16. Текущее состояние работы

Созданы проекты Protocol (контракты без зависимостей клиента), Remote (HTTP-клиент/provider) и Server (Linux ASP.NET Core/PostgreSQL). Сервер зависит только от Protocol и Npgsql, не от Windows, SQLite или парсеров агентов. CLI выбирает Git/HTTP по URL; init/join guards защищают текущую конфигурацию.

API-токен удалён из реализации. Версия протокола проверяется через `/v1/info`. Добавлены PostgreSQL-схема, Dockerfile, Compose, операционная инструкция и тесты реальной БД/HTTP, включая пределы размеров и сквозную синхронизацию двух профилей.

Linux-образ и Windows single-file CLI собираются. Итоговые результаты и ограничения проверок фиксируются в [server.md](server.md). Установка, миграция, коммит, push, релиз и развёртывание на Xeon в рамках подтверждения плана не выполняются.
