# Проверка slice 3 на Xeon — 2026-09-13

Проверка выполнена на выделенном Xeon, Intel Xeon E5-2680 v4, Windows 11 Pro, 16 ГиБ RAM. Сервер и PostgreSQL работали в Linux-контейнерах Docker Desktop 4.87.0 / Engine 29.7.2 / WSL2, а не на отдельной нативной Linux-ОС. Compose 5.4.0; тестовый runner на Xeon использовал установленный .NET SDK 10.0.103.

Пик памяти Linux API при нагрузке составил 845 905 920 байт (около 807 МиБ), OOM не было. PostgreSQL достиг лимита 1 ГиБ с перераспределением памяти, но без OOM. Это конкретный нагрузочный прогон, а не гарантия ёмкости для любого числа клиентов.

Первый прогон отдельной тестовой БД с искусственно уменьшенным лимитом 512 МиБ закончился OOM и восстановлением PostgreSQL: 24 теста прошли, 11 упали вследствие недоступности БД. Событие OOM подтверждено Docker. После приведения лимита к 1 ГиБ, указанному в Compose, все 35 тестов прошли. Не снижайте лимит до 512 МиБ при сохранении двух одновременных объектов по 100 МиБ.

Из SSH-сеанса штатный Windows credential helper Docker Desktop не смог получить credentials (`A specified logon session does not exist`). Для загрузки публичных образов использована отдельная конфигурация Docker в тестовом каталоге: существующие credentials и настройки Docker не изменялись. Образ API собран из локальных исходников непосредственно на Xeon, с digest базовых образов из `Dockerfile.server`.

При первом прогоне API был привязан к `127.0.0.1:58080`, восстановленный экземпляр — к `127.0.0.1:58081`. При прямой сетевой проверке новый тестовый экземпляр слушал только `<tailscale-server-ip>:58080`: фактический listener проверен через `Get-NetTCPConnection`. PostgreSQL основных тестовых проектов не публиковался на хосте. Порт `127.0.0.1:55433` использовался только отдельной одноразовой БД для автоматического suite и удалён вместе с её контейнером.

Прямой HTTP-доступ по Tailscale проверен после явного разрешения пользователя на временные сетевые изменения. Два правила Windows Firewall разрешали порт только выбранному клиентскому ПК и самому Xeon; остальные IPv4-адреса блокировались. Для отрицательной проверки существующее блокирующее правило временно применено ко всем адресам: тот же клиент перестал устанавливать новые TCP-соединения. После возврата исключений доступ восстановился, revision репозитория сохранился. Тем самым проверено фактическое применение firewall к опубликованному порту Docker, включая возможность запретить клиенту доступ. Правила, порт, контейнеры, volumes и сети удалены по завершении проверки.

В обоих сетевых режимах подключение к LAN-адресу Xeon `<lan-ip>:58080` с самого Xeon не проходит. На прямом Tailscale endpoint также проверены HTTP 403 для Origin и постороннего Host. Отдельные проверки с независимого LAN/интернет-клиента или другого устройства, запрещённого ACL Tailscale, не выполнялись; центральные ACL/grants Tailscale не изменялись. API-токен не добавлялся.

Тестовые Compose-проекты: `agent-sync-xeon-8bf16a` и `agent-sync-xeon-restore-8bf16a`. Их контейнеры, volumes и сети удалены после проверки. Существующие `steaminv-web` и `open-webui` не изменялись. Реальная история агентов и установленный agent-sync не использовались; постоянное развёртывание, миграция, коммит, push и релиз не выполнялись.
