# agent-sync — Project Context

## Project Overview

`Agent History Sync` — приложение командной строки для Windows, которое переносит историю Codex, Grok CLI, Claude Code и Continue между компьютерами через зашифрованный приватный репозиторий GitHub. Оно также предоставляет терминальные экраны для просмотра, поиска, экспорта, локального удаления и копирования диалогов между агентами. Названия и описания сессий хранятся отдельно от файлов агентов и синхронизируются вместе с историей; в текущем рабочем дереве добавлена синхронизация файлов памяти Claude.

**Platform**: Windows 11 x64, `.NET 10`, целевая платформа `net10.0`\
**Language**: `C# 14`, `PowerShell` для установки и выпуска\
**Domain**: инструменты разработчика, история AI-агентов, зашифрованная синхронизация

Публичная команда — `agent-sync`, исполняемый файл — `agent-sync.exe`. Имена решения, проектов, пространств имён и каталогов состояния сохраняют префикс `CodexHistorySync` для совместимости с существующими установками.

## Architecture Overview

`CliComposition` собирает зависимости по выбранному режиму запуска. Команды синхронизации используют `DefaultCliServices`, `CoreCliSyncRuntime` и общий `SyncEngine`; локальные экраны создают каталог и операции над сессиями независимо от конфигурации репозитория. `Core` содержит форматы, планирование, криптографию и файловые операции; проекты `Git` и `Windows` предоставляют инфраструктуру через интерфейсы.

Синхронизация сравнивает три состояния: локальные объекты, аутентифицированный удалённый снимок и последнюю успешную базу сравнения (`baseline`). Сначала подготавливаются данные и, если требуется, публикуется удалённый снимок; затем применяются локальные изменения с резервными копиями и журналом восстановления, после чего сохраняется новое состояние устройства.

```
                     agent-sync.exe / CliComposition
                                  │
             ┌────────────────────┼─────────────────────┐
             ▼                    ▼                     ▼
   sync / push / pull     --manage / --sessions        update
   init / join / status   LocalSessionCatalog      SelfUpdateService
             │            Conversion / Annotations      │
             ▼                    │                GitHub Releases
      DefaultCliServices          │                + SHA-256 asset
             │                    │
             ▼                    ▼
        SyncEngine        Локальные каталоги агентов
      ┌──────┼─────────┐     Codex / Grok / Claude / Continue
      ▼      ▼         ▼
  Scanners  ThreeWay  RepositoryCrypto
  / Writer  Planner       │
      │      │             ▼
      │   LocalState   IStorageProvider
      │   / Backups        │
      │   / Conflicts      ▼
      └─────────────── GitStorageProvider → private GitHub repo

  Windows: DPAPI + обнаружение Codex + задача AgentHistorySync
```

`--manage` работает без сети. `--sessions` не обращается к репозиторию синхронизации, но по клавише `T` может отправить сокращённый текст выбранного диалога на явно настроенный сервер генерации названий.

## Project Components

### 1. Командное приложение — `CodexHistorySync.Cli`

**Type**: консольное приложение\
**Location**: `src/CodexHistorySync.Cli/`\
**Purpose**: обработка команд, сборка зависимостей и взаимодействие с пользователем

- `Program.cs` передаёт аргументы в `CliApplication` и обрабатывает отмену через `Ctrl+C`.
- `CliApplication` разбирает команды, выполняет проверки и возвращает стабильные коды завершения.
- `DefaultCliServices` реализует сценарии инициализации, присоединения, диагностики и синхронизации.
- `SystemCliAdapters.cs` содержит `CliComposition` и адаптеры конфигурации, хранилища, процессов и среды выполнения.
- `Management/` содержит состояния и приложения менеджера/просмотрщика, интерфейсы представлений и реализации на `Spectre.Console`.
- `AgentWorker` выполняет фоновую синхронизацию; `GitHubReleaseSource` и `DefaultSelfUpdateOperations` связывают самообновление с установленным исполняемым файлом.

**Dependencies**: `Core`, `Git`, `Windows`, `Spectre.Console`.

### 2. Доменная логика — `CodexHistorySync.Core`

**Type**: библиотека\
**Location**: `src/CodexHistorySync.Core/`\
**Purpose**: модели данных, синхронизация, конвертация и безопасное изменение локальных файлов

| Область | Основные типы | Ответственность |
|---------|--------------|----------------|
| `Sync/` | `SyncEngine`, `ThreeWayPlanner`, `RepositorySyncLock` | Планирование, блокировка репозитория, повтор при гонке публикации |
| `Sync/`, `State/` | `BackupStore`, `ConflictStore`, `LocalStateStore` | Резервные копии, свидетельства конфликтов и база сравнения |
| `Codex/` | `SessionScanner`, `SessionJsonlNormalizer`, `CodexCompatibilityProbe` | Сканирование, компактное представление и проверка импорта Codex |
| `Codex/`, `IO/` | `CodexHistoryWriter`, `HistoryMutationBatch`, `IAtomicFileSystem` | Импорт поддерживаемых типов, атомарная запись, откат и восстановление |
| `Grok/`, `Claude/`, `Continue/` | `*Paths`, `*SessionScanner`, `*SessionPackage` | Пути, стабильное чтение и нативные пакеты соответствующих агентов |
| `Claude/` | `ClaudeMemoryScanner`, `ClaudeMemoryPackage` | Файлы памяти Claude как самостоятельные объекты |
| `Management/` | `LocalSessionCatalog`, `LocalSessionOperations`, `SessionExporter` | Каталог, операции над выбранной сессией и экспорт |
| `Conversion/` | `PortableConversation`, `ConversationDocument`, `*ConversationReader`, `*ConversationWriter` | Перенос пользовательских и ответных реплик между форматами |
| `Annotations/` | `SessionAnnotationStore`, `SessionDigest`, `OllamaSessionTitleSuggester` | Названия, описания и запросы к модели |
| `Crypto/`, `Providers/` | `RepositoryCrypto`, `IStorageProvider` | Аутентифицированное шифрование и контракт удалённого хранилища |
| `Update/` | `SelfUpdateService`, `ExecutableReplacer`, `ReleaseChecksum` | Проверка и замена бинарного файла с восстановлением при сбое |

Историческое имя `CodexHistoryWriter` не отражает весь текущий охват: через него также проходят пакеты Grok, Claude, Continue и отдельные маршруты аннотаций и памяти Claude.

### 3. Удалённое хранилище — `CodexHistorySync.Git`

**Type**: инфраструктурная библиотека\
**Location**: `src/CodexHistorySync.Git/`\
**Purpose**: чтение и публикация зашифрованного снимка через `Git`

- `GitStorageProvider` реализует `IStorageProvider`, поддерживает локальные репозитории для тестов и GitHub для рабочего сценария.
- `GitHubVisibilityVerifier` проверяет приватность репозитория через `gh`.
- Публикация создаёт коммит без родителей и обновляет `main` с проверкой ожидаемой ревизии через `--force-with-lease`.
- Ветка данных хранит один актуальный снимок. Это свойство репозитория данных, а не требование к истории исходного кода.
- После каждых трёх успешных публикаций выполняется очистка недостижимых объектов локального зеркала; её сбой не отменяет уже успешную публикацию.

**Dependencies**: `Core`, внешние `git` и `gh`.

### 4. Интеграция с Windows — `CodexHistorySync.Windows`

**Type**: инфраструктурная библиотека\
**Location**: `src/CodexHistorySync.Windows/`\
**Purpose**: ключи текущего пользователя, обнаружение процессов и фоновый запуск

- `DpapiKeyStore` сохраняет производный ключ с привязкой к текущему пользователю Windows.
- `CodexExecutableLocator` находит заданный или установленный исполняемый файл Codex.
- `CodexProcessDetector` проверяет процессы; неоднозначность или отказ доступа трактуются как активный Codex, чтобы отложить импорт.
- `AgentScheduler` управляет принадлежащей приложению задачей `AgentHistorySync` при входе пользователя; действие задачи — абсолютный путь к приложению с аргументами `agent run`.
- `WindowsNotifier` сообщает о состоянии фоновой синхронизации без текста диалогов.

**Dependencies**: `Core`, Windows `DPAPI`, Task Scheduler.

## Data and Synchronization

### Поддерживаемые данные

Пути в таблице указаны относительно `%USERPROFILE%`, если не отмечено иное.

| Источник | Локальные данные | Единица синхронизации |
|----------|-----------------|----------------------|
| Codex | `.codex/sessions/`, `.codex/archived_sessions/` | Нормализованный `JSONL` активной или архивной сессии |
| Grok CLI | `.grok/sessions/<project>/<uuid>/` | Пакет `chat_history.jsonl` и, при наличии, `summary.json`; идентификатор `g-<uuid>` |
| Claude Code | `.claude/projects/<project>/<uuid>.jsonl` | Транскрипт, `cwd` и сохранённое имя каталога проекта; идентификатор `cl-<uuid>` |
| Continue | `.continue/sessions/<uuid>.json`, `.continue/sessions/sessions.json` | Файл сессии вместе с её записью общего индекса; идентификатор `co-<uuid>` |
| Аннотации | `%LOCALAPPDATA%/CodexHistorySync/annotations/` | Название и описание одной сессии, отдельно от нативной истории |
| Память Claude | `.claude/projects/<project>/memory/*.md` | Один Markdown-файл, включая `MEMORY.md`; идентификатор `cm-<hex(project)>.<name>` |

Codex и Grok перед отправкой сокращаются: исключаются тяжёлые технические записи и вложенные изображения, ограничиваются отдельные строки. Нормализация не переписывает исходные файлы при `push`; `pull` и `sync` могут импортировать, заменять и удалять локальные данные по результатам плана. Claude-транскрипты и файлы Continue передаются в собственных пакетах, а память Claude нормализует переводы строк без усечения текста.

### Правила согласования

1. `SyncEngine` берёт блокировку репозитория и проверяет оставшиеся журналы незавершённых локальных изменений.
2. Сканеры читают доступные источники параллельно и фиксируют нестабильные, исключённые или непроверенные объекты.
3. Проверяется зашифрованный удалённый индекс и соответствие набора файлов его непрозрачным идентификаторам; нужные тела объектов загружаются и проверяются по мере использования.
4. `ThreeWayPlanner` сравнивает локальную версию, удалённую версию и `baseline`, формируя загрузки, отправки, удаления и конфликты.
5. Подготовленные изменения публикуются с проверкой ревизии. При конкурирующей публикации выполняется повторное чтение и планирование, максимум пять попыток.
6. Локальные изменения проходят через проверку пути и ожидаемого содержимого, резервную копию и атомарную запись; новое состояние сохраняется после их применения.

Отсутствующий каталог агента не означает удаление всех его сессий. Непросканированные типы считаются неопределёнными; загрузки для отсутствующего агента откладываются с `skipped-no-agent-home`, а исключённые объекты не превращаются в удаляющие записи (`tombstones`).

### Особенности форматов и активности

- Внутренние потоки Codex с признаком `subagent` исключаются из каталога и новых отправок; ранее опубликованные копии автоматически не удаляются.
- В менеджере активность Codex определяется блокировками потоков, Grok — `active_sessions.json` и живым процессом. Перед изменением выбранная сессия проверяется повторно.
- Claude-сессия откладывается при работающем `claude` и записи транскрипта за последние 30 секунд. При нескольких файлах одного идентификатора выбирается самый свежий, затем более длинный, затем по пути.
- Continue откладывается по давности записи в пределах 30 секунд. При импорте обновляется запись только нужной сессии в `sessions.json`; остальные записи сохраняются.
- Межагентное копирование сохраняет текст реплик пользователя и ассистента, создаёт новый нативный идентификатор и не переносит системные сообщения, reasoning и результаты инструментов.
- Копия для Codex получает `source=cli` и настроенный `model_provider`. При доступном Codex `CodexSessionRegistrar` регистрирует опубликованный файл через `thread/read` и проверяет идентификатор и путь в `thread/list` с `useStateDbOnly=true`; проверка совместимости также использует предварительно инициализированный профиль. Сбой регистрации сохраняет единственную копию и сообщает о частичном завершении.
- Каждый ответ при копировании в Codex записывается как `response_item` и как событие `agent_message`: без второго интерфейс показывает только вопросы. До публикации проверка сравнивает полный текст, роли и порядок всех сообщений с `thread/read(includeTurns=true)`. Канал app-server явно использует UTF-8, включая Windows.
- Конфликтующие версии целого объекта сохраняются зашифрованными. Автоматического построчного слияния диалогов, аннотаций или памяти нет.

## Configuration and Local State

### Расположение файлов

Исполняемый файл устанавливается в `%LOCALAPPDATA%/Programs/CodexHistorySync/agent-sync.exe`. Состояние приложения хранится отдельно:

```
%LOCALAPPDATA%/CodexHistorySync/
├── config.json                  # Подключённый репозиторий и устройство
├── titles.json                  # Настройка генерации названий
├── keys/                        # Производные ключи под защитой DPAPI
├── annotations/                 # Локальные названия и описания
├── logs/                        # Журналы фонового агента
└── repositories/<repository-id>/
    ├── state.json               # База сравнения и успешная удалённая ревизия
    ├── maintenance.json         # Счётчик обслуживания зеркала
    ├── git/                     # Локальное зеркало репозитория данных
    ├── backups/                 # Резервные копии перед изменением истории
    ├── conflicts/               # Зашифрованные версии конфликтов
    └── staging/                 # Подготовленные данные и журналы изменений
```

### Переменные окружения

| Переменная | Назначение |
|------------|------------|
| `CODEX_HOME` | Альтернативный каталог Codex |
| `GROK_HOME` | Альтернативный каталог Grok |
| `CLAUDE_CONFIG_DIR` | Альтернативный каталог Claude |
| `CONTINUE_GLOBAL_DIR` | Альтернативный каталог Continue |
| `CODEX_EXE` | Явный абсолютный путь к исполняемому файлу Codex |
| `AGENT_SYNC_TITLE_ENDPOINT` | Сервер названий; переопределяет сохранённую настройку |
| `AGENT_SYNC_TITLE_MODEL` | Модель генерации; по умолчанию в коде `qwen3:8b` |
| `AGENT_SYNC_TITLE_LANGUAGE` | Язык названий: `auto`, `ru`, `en` |

Пример настройки генерации названий для локального сервера:

```powershell
agent-sync titles set http://localhost:11434 --model qwen3:8b --language ru
agent-sync titles test
agent-sync titles
```

Адрес по умолчанию отсутствует. Разрешены `localhost`, loopback и поддерживаемые частные IP-адреса; произвольные DNS-имена отклоняются. К базовому адресу добавляется `/api/chat`. `titles test` отправляет пример диалога; в просмотрщике `T` отправляет сокращённые реплики только выбранной сессии, а `A` позволяет задать название и описание вручную.

## Build and Usage

### Сборка и проверка

Команды выполняются из корня репозитория в Windows с установленным `.NET SDK 10`:

```powershell
dotnet restore CodexHistorySync.sln
dotnet build CodexHistorySync.sln -c Debug --no-restore
dotnet test CodexHistorySync.sln -c Debug --no-build
dotnet run --project src/CodexHistorySync.Cli -- --help
```

В тестах используются временные каталоги и синтетические сессии. Интеграционные проверки охватывают сходимость двух устройств, гонки публикации, конфликты, повреждённые данные, восстановление после сбоев, границы путей, локальные экраны и выпуск приложения.

```powershell
dotnet publish src/CodexHistorySync.Cli -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -o artifacts/win-x64
.\artifacts\win-x64\agent-sync.exe --version
```

Результат публикации — `artifacts/win-x64/agent-sync.exe`. `scripts/publish-release.ps1 -Version X.Y.Z` создаёт и отправляет тег `vX.Y.Z`; это запускает `.github/workflows/release.yml`, который публикует бинарный файл и контрольную сумму `SHA-256`. Текущий workflow выполняет сборку публикации, но не содержит шага `dotnet test`.

### Первое подключение

Для `init` нужен заранее созданный пустой приватный репозиторий данных; рабочий сценарий принимает `HTTPS`-адрес GitHub. Парольная фраза вводится интерактивно со скрытым вводом.

```powershell
# Первый компьютер
gh auth status
agent-sync init https://github.com/OWNER/agent-history-sync-data.git
agent-sync push
```

```powershell
# Следующий компьютер: предварительный просмотр, затем применение
agent-sync join https://github.com/OWNER/agent-history-sync-data.git
agent-sync join https://github.com/OWNER/agent-history-sync-data.git --apply
agent-sync sync
```

`join` без `--apply` не сохраняет ключи, конфигурацию и историю. При наличии Codex выполняется проверка импорта в одноразовом профиле; неудачная проверка блокирует подключение, а отсутствие автоматически обнаруженного исполняемого файла допускается с предупреждением.

### Повседневные команды

| Команда | Действие |
|---------|----------|
| `agent-sync status` | Аутентифицированное сравнение состояния без применения изменений |
| `agent-sync doctor` | Проверка окружения, доступа, ключа и совместимости |
| `agent-sync push` | Только публикация локальных изменений |
| `agent-sync pull` | Только получение и применение удалённых изменений |
| `agent-sync sync` | Двусторонняя синхронизация |
| `agent-sync --manage` | Локальные панели агентов, копирование и удаление |
| `agent-sync --sessions` | Просмотр, поиск, экспорт и аннотации |
| `agent-sync conflicts` | Список неразрешённых конфликтов |
| `agent-sync resolve CONFLICT_ID --keep-local` | Выбрать локальную версию конфликта |
| `agent-sync resolve CONFLICT_ID --keep-remote` | Выбрать удалённую версию конфликта |
| `agent-sync agent install` / `agent-sync agent uninstall` | Установить или удалить фоновую задачу |
| `agent-sync update --check` / `agent-sync update` | Проверить выпуск или обновить установленный бинарный файл |

В просмотрщике `/` фильтрует список либо ищет в открытом тексте в зависимости от фокуса; `E` экспортирует диалог в `%USERPROFILE%/Documents/agent-sync/`. Локальное удаление само по себе не публикует `tombstone`: следующая синхронизация отдельно определяет результат по трём состояниям.

### Автоматизация и коды завершения

Фоновый `AgentWorker` использует тот же `SyncEngine`. При активном Codex выполняются отправка и предварительное чтение; после завершения процессов выдерживается двухсекундное окно покоя, затем разрешается двусторонняя синхронизация. Повтор после ошибок начинается с 30 секунд и увеличивается до 30 минут.

| Код | Значение |
|-----|----------|
| `0` | Успешное завершение |
| `1` | Ошибка выполнения, сети или файлового ввода-вывода |
| `2` | Некорректная команда или аргументы |
| `3` | Не пройдена проверка безопасности или совместимости |
| `4` | Остались неразрешённые конфликты |

## Security and Compatibility Constraints

### Данные и восстановление

- Индекс и объекты шифруются независимо через `AES-256-GCM` в формате `CHS1`; аутентифицируются версия схемы, логический идентификатор и тип объекта.
- `Argon2id` выводит 32-байтовый ключ. Параметры по умолчанию в коде: память `65 536 KiB`, 3 прохода, параллелизм 2; парольная фраза не сохраняется.
- Публичный манифест содержит параметры и аутентификатор, а не пароль или ключ. Кэш `DPAPI` привязан к текущему пользователю Windows.
- Сканеры ограничены разрешёнными каталогами и форматами. Файлы авторизации, базы `SQLite`, системные журналы и конфигурация агентов не входят в синхронизацию; текст транскрипта сам может содержать записанные агентом данные.
- Перед заменой или удалением создаются проверяемые резервные копии со сроком хранения по умолчанию 30 дней. Локальные резервные копии и временные данные требуют защиты профиля пользователя.
- Ошибка аутентификации или неизвестный формат останавливают обработку до импорта. Неудачное локальное применение откатывается через `HistoryMutationBatch`; при неполном откате сохраняются данные для восстановления.
- `resolve CONFLICT_ID --export-both C:\Recovery\new-directory` экспортирует обе версии в новый каталог и оставляет конфликт неразрешённым.

### Контракты, которые важно сохранять

- Значения `ObjectKind` записываются в зашифрованный индекс как числа. Новые виды добавляются в конец перечисления; существующие значения нельзя перенумеровывать.
- До первой отправки нового типа все устройства должны поддерживать его: неизвестный тип блокирует чтение всего индекса. Это относится к Claude, Continue, аннотациям и новой памяти Claude.
- Нельзя восстанавливать имя проекта Claude из `cwd`: используется сохранённый сегмент каталога, поскольку преобразование пути в имя неоднозначно.
- Импорт Continue должен согласованно изменять файл сессии и её запись в общем индексе, сохраняя другие сессии.
- Хеш нормализованного объекта должен воспроизводиться после импорта и повторного сканирования; иначе возникают постоянные повторные отправки или конфликты.
- Аннотации записываются только в каталог приложения. Официальное название агента сохраняет приоритет в списке сессий.
- Проверки и тестовые фикстуры должны использовать синтетическую историю; реальные диалоги, ключи и конфигурация пользователя не должны попадать в исходный репозиторий.

### Known Issues and Limits

- Поддерживаемая рабочая платформа — Windows x64; переносимость отдельных библиотек не означает поддержку приложения в Linux/macOS.
- Сокращённые Codex/Grok-пакеты и межагентное копирование не сохраняют всю техническую историю исполнения; синхронизация вложений отключена.
- Слишком большой подготовленный объект пропускается при отправке с `skipped-oversized`; порог отправки в движке — около `95 MiB`.
- Одновременное изменение одной сессии на разных устройствах требует явного разрешения конфликта.
- Нет отдельной команды восстановления резервной копии и ротации ключа на месте; процедуры описаны в `docs/operations.md` и `docs/security.md`.
- Проверка Codex в `docs/compatibility.md` относится к конкретной сборке и дате, а не гарантирует совместимость с любым последующим форматом.
- Часть старых текстов в `README.md`, `docs/operations.md` и `docs/security.md` описывает более ранний охват агентов или границы сети. Для текущего поведения приоритет имеют реализация и соответствующие тесты.
